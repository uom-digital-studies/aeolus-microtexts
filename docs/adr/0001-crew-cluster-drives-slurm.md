# Use `targets` + `crew.cluster` to drive SLURM directly, rather than hand-written SLURM array scripts

The pipeline needs to submit LLM-analysis work (crossing research question, model, context variant, and unit of analysis) to a SLURM cluster. The existing approach was a bash script (`submit-sentiment-jobs.sh`) generating a SLURM job array, with a plain `Rscript` CLI called per array task. We considered keeping this pattern, with a `targets` pipeline invoked inside each array task to handle the sub-grid for that task's model (option B), versus having `targets` submit and manage SLURM jobs itself via `crew.cluster` (option A).

We chose **option A**: `targets`, via `crew.cluster` controllers, submits SLURM jobs directly. Parallelization is coarse — one controller/worker group per model, not per grid cell — because Ollama server startup and model-pull cost per SLURM task dominates, and the dataset is small enough that finer-grained parallelism isn't worth the overhead. Workers are pinned per model group so the Ollama server and pulled model stay warm across all research-question/context/unit combinations for that model, rather than being re-pulled or restarted.

This means the existing hand-written `.slurm`/bash orchestration scripts are superseded and will be deleted once the new pipeline is validated (first in a Dockerised SLURM cluster, then on the real HPC cluster). The trade-off accepted: less direct visibility into raw `sbatch` mechanics day-to-day, in exchange for `targets`' caching (avoiding recomputation of unchanged grid cells) and a single, reproducible R-level description of both the analysis grid and the SLURM resource requirements (the latter factored into `slurm-resources.yml`).
